# Coolcode harness quality improvement plan

Created: 2026-11-01T00:30:03+05:30 (Asia/Kolkata, UTC+05:30)
Status: proposed implementation plan; this document does not implement the changes below.

## Objective

Improve the reliability and maintainability of code produced by Coolcode. Use the
Kafka demo as a concrete evaluation case, and adapt useful OpenCode mechanisms.
Measure whether the harness completes the user's full request, detects failures,
retains requirements, and reports verification accurately.

The reviewed project is `/home/rushikeshg25/personal/exactly-one-delivery-kafka`.
This review left its source, dependencies, Git state, and services unchanged.

## Findings from the Kafka project

The project is a reasonable educational v0: strict TypeScript, small modules,
real lost-ACK fault injection, exact record assertions, fencing checks, and a
clear statement that single-broker results are not production guarantees.
The following gaps matter more than cosmetic style changes:

1. **Requested delivery work remains incomplete.** The directory is not a Git
   repository. `context.md:18` also records that Git initialization and five
   requested commits were outstanding. The harness needs a durable record of
   explicit deliverables and a completion check against them.
2. **Dependency installation is not reproducible across the documented paths.**
   `Dockerfile:3-4` uses `npm install`, but no `package-lock.json` is present.
   A `bun.lock` exists while Docker and README use npm. Choose and consistently
   apply one package manager and lockfile, then use its frozen install command.
   The pinned runtime/dependency versions should receive a separate current
   support and vulnerability check; this review did not establish any CVE.
3. **The unit suite does not test the proxy's important network behavior.**
   `test/proxy.test.ts` contains three framing tests and one fencing-error test.
   It does not directly test correlation routing, ACK suppression exactly once,
   reconnect behavior, or persistence-check failure. The reported integration
   runs exercise the successful demonstration path, but do not replace those
   failure-path tests.
4. **Cleanup can stop early.** `src/layer1.ts:31-33` awaits producer disconnect
   before proxy close in the same finally block. A disconnect rejection skips
   proxy cleanup. Test cleanup failures and ensure all owned resources are
   released, while preserving the original error.
5. **Error traversal has a reproduced edge-case bug.** `src/layer2.ts:6-11`
   rejects direct self-reference but does not handle a two-object cause cycle.
   Calling `isFencing()` with that cycle produced `RangeError`. Use a visited
   set or an explicitly bounded traversal, with a regression test.
6. **Formatting and verification conventions are incomplete.** `package.json`
   has build/typecheck/test scripts, but no lint or formatting checks. Several
   control-flow and cleanup blocks are compressed onto one line. Add a small,
   project-appropriate formatting and lint setup rather than a large framework.

### Clarification: local node_modules

A missing host `node_modules` directory is normal for this Docker workflow.
`Dockerfile:4` installs dependencies under `/app` in the image, and
`Dockerfile:8` runs type checking and tests there. `scripts/verify.sh:5-10`
executes checks and demos in containers. Host installation is a separate path.
The harness should report the execution environment explicitly. Do not classify
absence of host dependencies as a defect or evidence that tests were skipped.

## Harness findings

### Tool outcomes need stronger contracts

In `internal/tools/shell_tools.go`, the exit code and error explanation are in
`ToolResult.Display`; stdout/stderr form `LLMResult`. The processor feeds only
`LLMResult` back into the conversation. A command that exits unsuccessfully
without output can therefore give the model no explicit failure signal even
though the UI knows it failed. Return status and exit code to the model as well.

`internal/tools/fs_tools.go` describes `expected_replacements`, but the edit
loop stops once that many matches have been replaced. It does not require the
actual match count to equal the expected count before writing. With the default
of one, an ambiguous old string can silently change the first occurrence.
Enforce the match contract before any mutation.

### Requirements can be lost during context reduction

`internal/agent/processor.go` requests a compaction summary under 200 words.
`internal/agent/context.go:290` summarizes message text, skipping textless tool
calls and their argument payloads. Explicit work such as commits, package-manager
choices, and unfinished validation needs structured preservation. This is a
plausible contributor to incomplete work, not a proven explanation of the
historical Kafka session.

### The prompt is generic, and instruction loading is limited

`internal/agent/prompts.go` already tells the agent to inspect, plan, implement,
and verify. Repeating those broad instructions will not repair the tool contracts.
It lacks a concrete greenfield-project checklist and an evidence-backed final
completion check.

`internal/memory/memory.go` loads project `COOLCODE.md`, falling back to the global
file. It does not combine scoped `AGENTS.md` instructions. The system prompt also
marks repository instructions as untrusted data. Introduce an explicit trust and
precedence model for user-approved project guidance, while retaining the
untrusted treatment of fetched pages and arbitrary tool output.

## OpenCode mechanisms to adapt

- **Structured compaction.** OpenCode's current summary template preserves the
  objective, user requirements, decisions, completed/active/blocked work, next
  steps, and consequential Git workflow state. Adapt those fields and retain
  exact unresolved user requests.
  [Compaction implementation](https://github.com/anomalyco/opencode/blob/dev/packages/core/src/session/compaction.ts)
- **Clear edit contracts.** Its edit tool requires a unique match by default,
  detects ambiguity, and provides useful mismatch feedback. Apply that principle
  to Coolcode's existing edit and patch tools before adding more tools.
  [Edit implementation](https://github.com/anomalyco/opencode/blob/dev/packages/core/src/tool/plugin/edit.ts)
- **Scoped project guidance.** Its rules support project/global `AGENTS.md` and
  explicit instruction files. Adapt precedence and scope with a clear trust boundary.
  [Rules documentation](https://opencode.ai/docs/rules/)
- **Feedback after edits.** OpenCode supports language-specific formatters and
  diagnostics. Its current documentation says formatters are opt-in and notes
  that diagnostic CLI commands can be preferable to LSP. Start with existing
  build/lint/typecheck commands; add optional LSP only where it helps.
  [Formatters](https://opencode.ai/docs/formatters/), [LSP guidance](https://opencode.ai/docs/lsp/)
- **Focused prompt guidance.** Current OpenCode prompts include tool-specific
  guidance and concise autonomy/workflow instructions. Use a short common prompt
  plus small validated mode/model additions. Do not assume copying a larger
  prompt will improve results.
  [System prompt assembly](https://github.com/anomalyco/opencode/blob/dev/packages/core/src/session/system-prompt.ts),
  [GPT prompt](https://github.com/anomalyco/opencode/blob/dev/packages/core/src/plugin/system-prompt/gpt-astra.txt)

Sources were checked on the document creation date. Links point to a moving dev
branch; recheck the owning source before implementing an adapted mechanism.

## Implementation sequence

Use one commit per meaningful change. Shared reliability improvements should be
reviewed for both main and dev; subscription routing and detailed trace collection
remain dev-only. Each step below should be independently testable.

| Step | Change | Acceptance check |
| --- | --- | --- |
| 1 | Establish a small baseline evaluation suite | Run fixed tasks with fixed model/effort/tool settings. Record task completion, unsupported claims, invalid edits, time and tokens. Include the Kafka request and smaller failure fixtures. |
| 2 | Return structured execution evidence to the model | A silent nonzero command is visible as failed, with exit code, command, cwd, environment label, timeout/cancellation and truncation status. Tool payloads remain bounded and redacted. |
| 3 | Enforce exact edit contracts | Zero, ambiguous, and unexpected-count matches fail without modifying files. Exact expected matches succeed; external edits between read and write cannot be overwritten silently. |
| 4 | Persist requirements and improve compaction | Preserve deliverables, constraints, user corrections, approvals, blockers and verification state across two forced compactions and session restore. Git requirements remain pending until supported by actual Git results. |
| 5 | Add scoped instruction loading and a greenfield workflow | Discover the language, package manager, runtime, build/test commands and user-approved project rules. New projects get a consistent lockfile, useful tests, and setup instructions. Conflicting/untrusted instructions cannot expand permissions. |
| 6 | Feed formatting and diagnostics into the repair loop | Run configured checks after coherent batches of edits, feed failures back to the model, and repair within a bounded attempt budget. Distinguish missing checks from passing checks. Start with CLI diagnostics; make LSP optional. |
| 7 | Add a completion check against requested outcomes | Before declaring completion, reconcile deliverables with tool evidence. Report host versus Docker checks, failures, unrun checks, Git state and remaining blockers. Skip this machinery for simple conversational answers. |
| 8 | Compare the candidate against the baseline | Repeat representative tasks, including interruptions and compaction. Require no regression in correctness or authorization handling. Measure completion rate, unsupported-success claims, latency and token cost before promoting prompt changes. |

### Proposed prompt additions

Keep these operational and short, then evaluate their effect:

1. Extract the user's explicit deliverables and constraints. Keep unfinished work
   active when follow-up messages add requirements or ask for status.
2. For a new project, establish a runnable development path, package manager,
   lockfile, verification commands, and appropriate failure-path tests.
3. For resource-owning code, inspect error, timeout, cancellation, and cleanup
   paths. Prefer readable control flow and small modules.
4. Treat tool failures and approval declines as distinct states. Explain a real
   blocker accurately; never attribute an automatic block to a user decision.
5. Run the relevant checks and identify where they ran. A passing Docker test
   does not establish that host dependencies are installed.
6. Finish only when the explicit deliverables are satisfied or clearly identify
   what remains blocked. Report verification evidence without inventing results.

The completion check must respect read-only requests, user cancellation, and
ungranted permissions. It must not loop forever or force an installation merely
because a local dependency folder is absent.

## Evaluation cases and pass criteria

- Empty TypeScript repository, Docker-first setup, explicit Git/commit request.
- Existing repository with its own package manager, lockfile, and instructions.
- A command that exits nonzero with no stdout/stderr.
- A repeated edit target and a file modified externally after reading.
- A cleanup failure, a timeout, and a cyclic error chain.
- Approval declined, then later approved; new user input during a tool run.
- Two forced compactions while an explicit deliverable remains incomplete.
- Docker-only dependency installation with no host `node_modules` directory.

For each case retain the prompt/model settings, redacted trace, source diff,
actual test results, and final response. Score concrete outcomes rather than the
length of the answer or number of tools used. Deterministic harness regressions
must pass; live model evaluations should use repeated trials and disclose
variation. Do not execute tool calls merely because they appear in a saved trace.
