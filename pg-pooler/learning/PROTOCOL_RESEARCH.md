# PostgreSQL pooler protocol research

Verified 2026-09-15 against PostgreSQL 17 documentation and the current PgBouncer documentation. This is planning research for a learning project, not a claim of full PostgreSQL compatibility.

## Protocol facts and design implications

1. **Startup and ordinary messages have different framing.** Ordinary messages contain a one-byte type followed by a four-byte length; the length includes its own four bytes but excludes the type. The initial startup message has no type byte. Its body starts with protocol version `196608` (3.0), followed by zero-terminated name/value pairs. `user` is required; `database` defaults to the user. Design implication: separate startup parsing from typed-message parsing, validate lengths, and expect fragmented/coalesced TCP reads. A partial message followed by transport failure means abandoning the connection. Sources: [messaging overview](https://www.postgresql.org/docs/17/protocol-overview.html), [message formats](https://www.postgresql.org/docs/17/protocol-message-formats.html).

2. **Connection establishment is a state machine.** Before a normal startup packet, a client can send SSLRequest or GSSENCRequest. SSL negotiation replies are single bytes (`S`/`N`), not ordinary typed messages. A no-TLS learning server can reply `N` to an SSLRequest and then read the startup packet; clients requiring TLS will disconnect. Successful authentication is followed normally by ParameterStatus, BackendKeyData and finally ReadyForQuery. AuthenticationOk alone does not mean startup is complete. Sources: [startup and SSL flow](https://www.postgresql.org/docs/17/protocol-flow.html), [message formats](https://www.postgresql.org/docs/17/protocol-message-formats.html).

3. **ReadyForQuery carries transaction state.** `Z` has a one-byte status: `I` = idle outside a transaction block; `T` = inside a transaction; `E` = failed transaction block. A transaction pool must keep a backend pinned for both `T` and `E`; an error response or CommandComplete is not a release signal. Design implication: use protocol state rather than searching SQL text for BEGIN/COMMIT. Even `I` is only an eligibility condition: release also requires complete response processing, no outstanding work and successful cleanup. Sources: [ReadyForQuery format](https://www.postgresql.org/docs/17/protocol-message-formats.html), [simple-query and extended-query flow](https://www.postgresql.org/docs/17/protocol-flow.html).

4. **Session pooling comes before transaction pooling.** PgBouncer session mode assigns a server connection for the client's whole session, releasing it when the client disconnects. Transaction mode assigns one only during a transaction and requires application cooperation around session features. Persistent SET/RESET, LISTEN, SQL PREPARE/DEALLOCATE, session advisory locks and certain temporary-table/cursor patterns are incompatible with transaction mode. Current PgBouncer can support protocol-level prepared plans when `max_prepared_statements` is nonzero; it is inaccurate to say every kind of prepared statement is unsupported. Source: [PgBouncer features and compatibility table](https://www.pgbouncer.org/features.html).

5. **Backend cleanup is real protocol work.** PgBouncer's default `server_reset_query` is DISCARD ALL, executed on release before another client receives the connection. It normally runs in session pooling only, not transaction pooling. PostgreSQL forbids DISCARD ALL inside a transaction block; its effects include RESET ALL, deallocating statements, unlistening, unlocking session advisory locks and discarding temporary resources. Learning-project recommendation: initially close a backend if the client disconnects with active/failed transaction, incomplete exchange or uncertain state; for a fully drained idle connection, run DISCARD ALL and consume its complete response through ReadyForQuery before reuse. Destroy the backend if reset fails. A later rollback-and-drain path is an explicit additional exercise. If the educational transaction mode resets on every release, label that a conservative project policy, not PgBouncer's default behavior. Sources: [PgBouncer reset settings](https://www.pgbouncer.org/config.html#server_reset_query), [PostgreSQL DISCARD](https://www.postgresql.org/docs/17/sql-discard.html).

6. **Frontend and backend authentication become separate responsibilities.** A dedicated TCP relay can forward startup/authentication between one client and one server. A reusable backend has already completed its own startup; each new frontend still needs the pooler's startup/authentication exchange. PgBouncer explicitly uses credentials both to authenticate incoming clients and log into outgoing servers. SCRAM stored secrets cannot generally be used by themselves to derive outgoing login credentials; PgBouncer documents specific conditions for SCRAM passthrough. Recommendation: begin with one explicit database/user and a loopback-only, disposable trust-authenticated PostgreSQL instance; reject other identities/startup options rather than silently treating them as equivalent. Add TLS and credential handling as a separate milestone. Sources: [PostgreSQL startup](https://www.postgresql.org/docs/17/protocol-flow.html), [PgBouncer authentication file and limitations](https://www.pgbouncer.org/config.html#authentication-file-format).

7. **Extended query has state and recovery rules.** Parse creates prepared statements; Bind creates portals; Execute uses a portal. At the end of an extended-query series Sync establishes the recovery boundary and produces ReadyForQuery. On an extended-query error the backend discards subsequent messages until Sync. Sync does not end an explicit BEGIN transaction. Pipelining requires counting ReadyForQuery responses against Sync messages, not counting CommandComplete messages. Recommendation: support simple-query traffic first, require compatible client configuration, explicitly reject unsupported typed frontend messages, then add extended query and pipelining as distinct exercises. Sources: [extended-query overview](https://www.postgresql.org/docs/17/protocol-overview.html), [extended query and pipelining](https://www.postgresql.org/docs/17/protocol-flow.html).

8. **Cancellation is an independent connection and a backend-reuse hazard.** A frontend opens a new connection and sends CancelRequest with backend PID and secret from BackendKeyData. PostgreSQL closes the cancellation connection without a direct reply; cancellation is inherently racy and the original query response remains authoritative. Design implication: never expose a reusable backend's real cancellation key as a permanent frontend identity. A pooler needs a virtual client key, mapping to its current backend lease, and synchronization preventing a delayed request from canceling another client's work. Until implemented, make cancellation explicitly unsupported and do not publish real reusable-backend cancellation credentials. Sources: [cancellation flow](https://www.postgresql.org/docs/17/protocol-flow.html), [CancelRequest and BackendKeyData formats](https://www.postgresql.org/docs/17/protocol-message-formats.html).

## Recommended learning scope

- Start with a disposable PostgreSQL 17 instance, Go standard-library networking, one user/database, protocol 3.0 and simple queries. Keep early trust/no-TLS behavior bound to loopback and document the client settings.
- Learn byte forwarding first with dedicated connections; then replace opaque forwarding with framed messages and explicit frontend/backend lifecycles before attempting reuse.
- Build bounded session pooling with exclusive leases, queue cancellation/timeouts, backend accounting, and cleanup verification. Reset responses belong to pooler maintenance and must never leak to the next client.
- Add transaction pooling only after proving session isolation and the I/T/E transitions, including errors, client disconnects and backend failures. Use cooperative SQL workloads rather than a naive SQL parser to promise broad feature restrictions.
- Defer extended query, prepared-statement virtualization, COPY, LISTEN/NOTIFY, cancellation, multi-user/startup-parameter tracking and production authentication/TLS. Simple-query COPY can enter a separate protocol state even without extended messages: the first version should terminate/discard safely on an unsupported COPY response rather than continue as an ordinary query.
- Validate behavior against real PostgreSQL as well as unit-level wire framing. Acceptance cases should include fragmentation, malformed lengths, failed explicit transactions, no response contamination across leases, reset failure, queue cancellation, and bounded backend counts. The learner implements each milestone; review should focus on invariants and observed behavior before revealing solutions.

The scope recommendations above are project design judgments derived from the cited protocol constraints, not requirements imposed by PostgreSQL or PgBouncer.
